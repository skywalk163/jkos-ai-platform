## 1. 总体策略

### 1.1 一个平台、三个租户

三个案例**不是三个独立项目**，而是同一平台代码库上的三个租户（对应设计文档 §8.4 多租户架构）：

```
                    ┌────────────────────────────────────┐
                    │        DSH AI 中台 (一个代码库)       │
                    │  CORE: 工作流引擎 / MCP网关 / LLM路由 │
                    │        事件总线 / 审计 / RBAC / 通知  │
                    ├────────────┬────────────┬──────────┤
                    │ 租户A       │ 租户B       │ 租户C     │
                    │ 编程项目中台 │ 自媒体中台   │ 酒厂中台   │
                    │ (DSH-Dev)  │ (DSH-Media)│ (DSH-Win) │
                    │ M1 交付     │ M2 交付     │ M3 交付   │
                    └────────────┴────────────┴──────────┘
```

**多租户验证路径**：M1 单租户裸奔 → M2 双租户（引入租户上下文与组件可见域）→ M3 三租户（配额、RBAC 命名空间全量生效）。

### 1.2 三案例定位

| 案例 | 定位 | 主要验证目标 | 外部依赖强度 |
|------|------|--------------|:--:|
| **案例2 编程项目中台** | 自举试验田（用平台开发平台） | CORE 全家桶：工作流引擎、MCP 网关、LLM 路由、人工干预、审计 | ★☆☆ |
| **案例3 自媒体中台** | 首个行业落地 + 案例1 的低成本预演 | 行业组件模式、内容生产管线、舆情组件、黑板式协作 | ★★☆ |
| **案例1 酒厂中台** | 企业级验证（设计文档锚点场景） | ERP/MES 集成、追溯链、RBAC 全量、联动事件、合规审计 | ★★★ |

### 1.3 开发顺序与理由（2 → 3 → 1）

**不按"酒厂优先"开发，理由**：

1. **依赖最轻者先行**：案例2 的外部依赖只有 Git（我们自己控制），案例3 是内容平台 API，案例1 需要 ERP/MES/门店/HR 五个系统集成（设计文档 §8.6.1 已论证）；
2. **自举（Dogfooding）**：案例2 就是开发团队自己——用中台的代码审查工作流审查中台自己的代码，第一周就能发现平台缺陷，反馈周期最短；
3. **案例3 为案例1 铺路**：见 1.4 横向复用地图——案例3 建成的两个横向组件直接构成酒厂 MVP 两个工作流的 60% 内核；
4. **风险后置到最有议价能力时**：案例1 涉及客户现场集成，等平台在案例2/3 上稳定后再进场，集成风险最低。

### 1.4 横向复用地图（本计划的核心杠杆）

三个案例的工作流存在大量**同构**，抽成两个横向组件，一次开发、两个案例受益：

```
横向组件 H1：内容生产管线 (ContentPipeline)
  ┌──────────────────────────────────────────────────┐
  │ 选题/输入 → 生成 → 风格适配 → 人工审 → 多渠道分发   │
  └──────────────────────────────────────────────────┘
   ├─ 案例3 自媒体：风格包=人设/IP调性，渠道=公众号/抖音/小红书/B站
   └─ 案例1 酒厂：  风格包=品牌规范/合规词库，渠道=门店物料/电商页/广告投放
                    （= 营销决策工作流 2.2 的内核）

横向组件 H2：舆情采集与情感分析 (SentimentHub)
  ┌──────────────────────────────────────────────────┐
  │ 多源抓取 → 清洗 → 情感打分 → 话题聚类 → 分级事件    │
  └──────────────────────────────────────────────────┘
   ├─ 案例3 自媒体：源=评论区/弹幕/私信，分级→回复策略
   │                （= 评论互动工作流的内核）
   └─ 案例1 酒厂：  源=新闻/微博/投诉，分级→危机预警 2.5 的风险等级表
                    （= 危机预警工作流的内核）
```

**行业专属部分**（不可复用，按案例定制）：

| 案例 | 专属组件 |
|------|----------|
| 案例2 | Git/CI 适配器、代码分析（规则引擎 + LLM 审查）、测试执行沙箱 |
| 案例3 | 各内容平台 API 适配器、发布排期、数据复盘报表 |
| 案例1 | MES/ERP/WMS/HR 适配器、批次追溯链（设计文档 2.6）、生产数据模型 |

**工作量影响估算**：案例1 MVP 的两个工作流（危机预警+营销决策）中，约 60% 的节点由 H1/H2 承担，案例1 现场开发量从"两个完整工作流"降为"适配器 + 数据模型 + 联动配置"。

## 2. 三案例需求画像

### 2.1 案例A（原案例2）：编程项目 AI 中台（DSH-Dev）

**目标用户**：5–20 人研发团队的小型创业公司（第一个客户就是我们自己）。

**解决痛点**：代码审查靠人肉且标准不一、缺陷修复无复现即改、测试覆盖率凭良心、文档永远过期、发布靠记忆。

**工作流清单**（5 条，均标注设计文档范式）：

| 编号 | 工作流 | 步骤链 | 协作范式 | 人工干预点 |
|------|--------|--------|----------|------------|
| D1 | 代码审查 | webhook 收 diff → 规则扫描 ∥ LLM 审查（黑板式并行）→ 汇总报告 → 评论区回帖 | 黑板式 | 报告误报标记（低风险） |
| D2 | 缺陷修复 | issue → 复现（跑出失败用例）→ 定位 → 修复补丁 → 单测 → 提交 PR | 管道式 | 补丁人工确认（中风险，8h 超时升级） |
| D3 | 单元测试生成 | 选定函数 → 用例设计 → 生成 → 运行 → 覆盖率报告 | 管道式 | 无（结果仅报告） |
| D4 | 文档同步 | 代码变更事件 → API diff → 文档更新草稿 → 人工审 → 合入 | 管道式 | 文档审核（低风险） |
| D5 | 发布工作流 | 版本号 → 构建 → 部署测试环境 → 冒烟 → 人工放行 → 生产 → 验证 | 管道式 | **生产放行（高风险，双人复核 + 自动驳回）** |

**外部依赖**：Git 平台（gitee/github 自托管均可）、Python 沙箱（跑测试）。**无 ERP/MES 类重集成**。

**验收 KPI**：D1 对本仓库每日自动审查并出报告；D2 从 issue 到 PR 人工只确认一次；D5 冒烟失败自动回滚（验证设计文档 §8.3）。

### 2.2 案例B（原案例3）：自媒体运营 AI 中台（DSH-Media）

**目标用户**：1–10 人自媒体团队/个人 IP。

**解决痛点**：选题靠灵感、一稿多平台改到吐、数据分散在各平台后台、评论区看不过来。

**工作流清单**（5 条）：

| 编号 | 工作流 | 步骤链 | 协作范式 | 人工干预点 |
|------|--------|--------|----------|------------|
| M1 | 选题策划 | 热点抓取 → 选题评估打分 ∥ 竞品分析（黑板式）→ 选题库 | 黑板式 | 选题定夺（低风险） |
| M2 | 内容生产 | 选题 → 大纲 → 初稿 → 人工改（字段级）→ 平台适配（×N 并行）→ 封面/配图 | 主从式（适配多候选择优） | **内容审核（高风险：发布不可逆，撤回预案前置）** |
| M3 | 发布管理 | 排期 → 定时发布 → 状态回执跟踪 | 管道式 | 排期调整（低风险） |
| M4 | 数据复盘 | 平台数据抓取 → 指标计算 → 归因分析 → 复盘报告 → 反哺选题库事件 | 管道式 | 无（报告推送） |
| M5 | 评论互动 | H2 舆情组件 → 情感分级 → 回复建议（负面→人工审，正面→或签自动回） | 主从式 | 负面评论回复审核（中风险） |

**外部依赖**：内容平台 API/爬虫（先公众号 + 小红书两个平台起步）、图片生成（可复用现有 OCR 插件反向思路，接外部生图 API）。

**验收 KPI**：每周 5 篇内容从选题到多平台发布 ≤4h 人工介入；M4 每周自动复盘报告；M5 负面评论 30 分钟内进入待审队列。

**战略意义**：M2 = H1 管线的首发载体；M5 = H2 组件的首发载体。**本案例建成之日，案例1 MVP 的内核已就绪**。

### 2.3 案例C（原案例1）：酒厂 AI 中台（DSH-Winery）

**目标用户**：酒厂企业管理层与生产/营销/品控部门（对应设计文档 §2.8 十个角色）。

**工作流清单**：完全按设计文档 §2 执行，MVP 阶段只交付 P0 两条（§8.6.1 修订结论）：

| 阶段 | 工作流 | 内核来源 | 本案例新增开发 |
|------|--------|----------|----------------|
| **MVP (P0)** | 危机预警（2.5） | **H2 舆情组件**（案例B M5 同款） | 风险等级表配置、危机团队角色与通知链、监管报备模板 |
| **MVP (P0)** | 营销决策（2.2） | **H1 内容管线**（案例B M2 同款） | 品牌规范/合规词库风格包、门店/电商渠道适配器、投放 ROI 数据回流 |
| P1 | 生产调度（2.1） | — | ERP/MES/门店适配器、需求预测、排程状态机 |
| P1 | 质量追溯（2.3） | — | 批次数据模型落地（2.6）、trace_node 链、LIMS 适配 |
| P2 | 新品研发（2.4） | 复用 D3 评审模式 | 评审角色、方案对比黑板 |

**外部依赖**：舆情源、门店/电商系统（P0）；ERP/MES/WMS/HR/LIMS（P1，按 §8.7 风险条目前置 POC 评估）。

**验收 KPI**：按设计文档 §2.7.1——负面舆情发现时延 ≤30 分钟、误报率 ≤10%、内容生产 ≤4h/批、联动事件（2.9）SENTIMENT.LEVEL_RAISED 触发营销暂停演练通过。

## 4. 里程碑计划（M0–M4）

### M0（第 1–2 周）：平台骨架

**目标**：CORE 层最小闭环，一个 hello 工作流经 API 触发→执行→审计留痕。

| # | 任务 | 产出 |
|---|------|------|
| 0.1 | SQLite 数据层：workflow_instance / workflow_step / audit_event / tenant 表 | `dsh_core/db/` |
| 0.2 | 工作流引擎 v0：状态机 + 管道式编排 + 实例持久化 + 崩溃续跑 | `dsh_core/workflow/` |

## 6. 技术决策记录（ADR）

| # | 决策 | 理由 | 推翻条件 |
|---|------|------|----------|
| ADR-1 | 存储 MVP 用 SQLite（WAL），P1 迁 PostgreSQL | 三案例 MVP 并发量低（<10 写/s），零运维 | 写入 >50/s 或需多机写 |
| ADR-2 | 事件总线内嵌（本地消息表）→ 后续 NATS | at-least-once 语义可自建，避免 MVP 引中间件运维 | 事件 >100/天 或跨主机消费 |
| ADR-3 | 前端用 Jinja2 极简页，不做 SPA | MVP 核心是审批闭环不是界面；单人开发精力聚焦引擎 | 多租户商用交付时（M4+） |
| ADR-4 | 工作流定义用 Python DSL（字典/装饰器）而非 BPMN XML | 与现有插件模式一致，LLM 生成/审查代码型 DSL 更可靠 | 需要业务人员自编排时（M4+ 再上可视化） |
| ADR-5 | 三租户共用一套 dsh_core，行业差异全部放 `tenants/*/` | 强制验证 §8.4.2 组件可见域设计 | — |
| ADR-6 | 平台部署延续 FreeBSD 192.168.0.82 + venv + start.sh | 环境已稳定，避免 M0 期引入容器化变量 | 客户要求专有云/容器交付（L1 档） |
