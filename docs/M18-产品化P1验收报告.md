## 三、M18.2 多租户 L2 物理隔离

### 3.1 数据层（真实隔离）

- **SQLite 模式**：L2 租户 = 独立 `.db` 文件，`create_schema` / `migrate_schema` / `drop_schema` 执行真实 SQL（`Database` + `MIGRATIONS` 幂等迁移，独立库自带三租户种子）。
- **PostgreSQL 模式（M19 就绪）**：`render_pg_schema_sql` 渲染可再生 DDL（含 V2 `approval_task`），假连接串全程零连接（延续 M4.4 契约）。
- **本次收口修复的缺陷**：

| 级别 | 缺陷 | 修复 |
| --- | --- | --- |
| 高 | 无 `close()`；`create_schema` 中 `migrate()` 异常会泄漏连接 | 新增 `close` / `close_all` / `unregister_tenant`；迁移失败先关连接再抛异常（不入连接表） |
| 中 | 存储路径依赖 `os.getcwd()`，工厂不可配置 | `data_dir` 参数 + `DSH_TENANT_DATA_DIR` 环境变量；工厂透传 `data_dir` |
| 中 | `tenant_code` 未校验即拼文件名（路径穿越风险） | 白名单正则 `^[a-z0-9][a-z0-9_-]{0,31}$`，非法抛 `ValueError` |
| 低 | 文件末尾缺换行 / SQLite-L1 误打 `[PG 就绪]` 日志 / `assert` 做控制流 / 死代码 `_connection_pools` | 逐项修正清理 |

### 3.2 运行时接线（默认关闭，零退化）

- `TenantIsolationConfig.from_env()`：`JKOS_TENANT_L2_ENABLED`（默认 false）、`DSH_TENANT_DATA_DIR`、`JKOS_TENANT_L2_CODES`（白名单，为空则按租户表 `isolation_level='L2'` 判定）。
- `AppComponents` 新增 `tenant_schemas` 字段与 `database_for()` / `engine_for()`：L2 租户拿到独立 `Database` 与专属 `WorkflowEngine`（独立仓储 + 共享 LLM/通知/JWT），按租户码缓存；`close()` 收敛全部租户连接。
- `build_components()` 启动时按租户表/白名单建库；单个租户失败即注销并降级 L1，**不阻塞启动**。
- API 层：`create_api_router/create_app` 支持 `engine_provider`（未显式传入时从 `engine.comps` 的 `AppComponents` 取 `engine_for`），审批路由按 `ctx.tenant_code` 取引擎；L2 模式下跨租户查询返回 **403**。
- **默认关闭时的等价性**：`tenant_schemas is None`、`database_for` 回落主库、`engine_for` 返回 `None`，行为与接线前完全一致（既有 999 用例零退化）。
