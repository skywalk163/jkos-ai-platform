## 1. 概述

### 1.1 设计目标

本设计文档以**酒厂企业**为锚点场景，构建 5 条端到端 AI 工作流，并以此为基础抽象出可复用的组件体系，最终覆盖 4 大行业（连锁餐饮、智能制造、医疗健康、教育培训），实现"**点 → 面 → 生态**"的渐进式覆盖策略。

### 1.2 平台架构总览

```
┌─────────────────────────────────────────────────────────┐
│                    企业 AI 中台 (DSH)                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐  │
│  │  基础设施层  │  │  协议层     │  │    能力层        │  │
│  │ PostgreSQL  │  │ MCP Server  │  │ 多模型路由      │  │
│  │ Redis       │  │ A2A Adapter │  │ 技能市场        │  │
│  │ MinIO       │  │ REST GW     │  │ 会话缓存        │  │
│  │ FFmpeg      │  │ WS/SSE      │  │ 工作流引擎      │  │
│  └─────────────┘  └─────────────┘  └─────────────────┘  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐  │
│  │  治理层     │  │  行业组件   │  │    功能组件      │  │
│  │ 审计日志    │  │ 酒类/餐饮   │  │ 数据采集/处理   │  │
│  │ 权限管理    │  │ 制造/医疗   │  │ AI 能力/工作流  │  │
│  │ 内容审核    │  │ 教育/通用   │  │ 自定义组件      │  │
│  └─────────────┘  └─────────────┘  └─────────────────┘  │
└─────────────────────────────────────────────────────────┘
         ▲              ▲              ▲
         │              │              │
    员工管理        门店系统        营销系统
    生产管理        新闻抓取        多媒体宣传
```

### 1.3 六大系统映射

| 系统 | 核心职责 | 涉及工作流 |
|------|----------|------------|
| 员工管理 | 组织架构、权限、绩效 | 全部（权限控制） |
| 门店系统 | 销售、库存、会员 | 生产调度、质量追溯 |
| 营销系统 | 策略、内容、投放 | 营销决策、危机预警 |
| 生产管理系统 | 计划、排产、质检 | 生产调度、新品研发、质量追溯 |
| 新闻抓取系统 | 舆情、行业资讯 | 营销决策、危机预警 |
| 多媒体宣传系统 | 内容生成、发布 | 营销决策、新品研发 |

### 1.4 设计原则

1. **事件驱动**：所有工作流以事件为触发源，支持异步/同步双模式
2. **Agent 协作**：每个步骤由独立 Agent 完成，通过 MCP/A2A 协议互联
3. **可观测性**：全链路 traceId，支持端到端追踪
4. **人工干预**：关键节点设置人工审批/确认点（Human-in-the-Loop）
5. **异常降级**：每条路径都有异常处理与回退策略

## 2. 酒厂场景详细工作流

### 2.1 智能生产调度工作流

**业务目标**：从门店销售预测出发，自动生成生产计划、采购需求、物流调度，实现"以销定产"。

#### 流程图

```
┌──────────────┐
│  门店销售数据  │
│  (POS/ERP)    │
└──────┬───────┘
       │ 触发条件：每日 00:00 或 库存<阈值
       ▼
┌──────────────────┐
│  Agent: 销售预测  │
│  输入: 历史销售   │
│  输出: 7日预测    │
│  模型: DeepSeek   │
└──────┬───────────┘
       │ 预测结果
       ▼
┌──────────────────┐
│  Agent: 需求聚合  │
│  输入: 各门店预测 │
│  输出: 总需求计划 │
└──────┬───────────┘
       │ 需求计划
       ▼
┌──────────────────┐
│  Agent: 生产排程  │
│  输入: 需求+产能  │
│  输出: 生产工单   │
│  ⚠️ 人工干预点    │
│  确认/调整工单    │
└──────┬───────────┘
       │ 生产工单
       ▼
┌──────────────────┐
│  Agent: 原料采购  │
│  输入: 工单+库存  │
│  输出: 采购单     │
│  ⚠️ 人工干预点    │
│  审批采购单       │
└──────┬───────────┘
       │ 采购单
       ▼
┌──────────────────┐
│  Agent: 物流调度  │
│  输入: 工单+仓库  │
│  输出: 配送计划   │
└──────┬───────────┘
       │ 配送计划
       ▼
┌──────────────────┐
│  Agent: 执行监控  │
│  输入: 工单状态   │
│  输出: 生产看板   │
│  异常: 延迟/缺料  │
└──────────────────┘
```

#### 触发条件

| 条件 | 类型 | 说明 |
|------|------|------|
| 每日 00:00 | 定时 | 全量预测 |
| 库存 < 安全库存 | 事件 | 触发紧急补产 |
| 门店促销活动 | 事件 | 增量预测 |
| 手动触发 | 人工 | 临时排产 |

#### 步骤详情

| 步骤 | Agent | 输入 | 输出 | 涉及系统 | 人工干预 | 异常处理 |
|------|-------|------|------|----------|----------|----------|
| 1. 销售预测 | 销售预测 Agent | 历史销售、促销、季节 | 7日销量预测 | 门店系统 | 无 | 无数据→使用均值 |
| 2. 需求聚合 | 需求聚合 Agent | 各门店预测 | 总需求计划 | 门店系统 | 无 | 冲突→人工仲裁 |
| 3. 生产排程 | 生产排程 Agent | 需求+产能+设备 | 生产工单 | 生产管理 | **确认/调整** | 产能不足→外协建议 |
| 4. 原料采购 | 采购 Agent | 工单+库存+供应商 | 采购单 | 生产管理 | **审批** | 缺货→替代方案 |
| 5. 物流调度 | 物流 Agent | 工单+仓库+路线 | 配送计划 | 生产管理 | 无 | 路线不可达→备选路线 |
| 6. 执行监控 | 监控 Agent | 工单状态+传感器 | 生产看板 | 生产管理 | 无 | 延迟→告警升级 |

#### 异常处理路径

```
异常: 产能不足
  ├─ 路径A: 外协生产 (自动生成外协工单)
  ├─ 路径B: 调整排期 (推迟非紧急订单)
  └─ 路径C: 人工决策 (通知生产经理)

异常: 原料缺货
  ├─ 路径A: 替代原料 (自动匹配替代方案)
  ├─ 路径B: 紧急采购 (加急通道)
  └─ 路径C: 生产调整 (减少产量/暂停)

异常: 物流延迟
  ├─ 路径A: 切换物流商
  ├─ 路径B: 客户沟通 (自动发送通知)
  └─ 路径C: 门店调货
```

### 2.2 智能营销决策工作流

**业务目标**：从新闻抓取与舆情分析出发，自动生成营销策略与内容，实现"数据驱动营销"。

#### 流程图

```
┌──────────────┐
│  新闻抓取系统  │
│  (RSS/爬虫)   │
└──────┬───────┘
       │ 触发条件：每 30 分钟增量 / 关键词命中
       ▼
┌──────────────────┐
│  Agent: 新闻采集  │
│  输入: 关键词列表 │
│  输出: 新闻数据   │
│  来源: 行业媒体   │
└──────┬───────────┘
       │ 新闻数据
       ▼
┌──────────────────┐
│  Agent: 趋势分析  │
│  输入: 新闻+历史  │
│  输出: 行业趋势   │
│  模型: DeepSeek   │
└──────┬───────────┘
       │ 趋势报告
       ▼
┌──────────────────┐
│  Agent: 竞品监控  │
│  输入: 竞品信息   │
│  输出: 竞品动态   │
└──────┬───────────┘
       │ 竞品动态
       ▼
┌──────────────────┐
│  Agent: 策略生成  │
│  输入: 趋势+竞品  │
│  输出: 营销策略   │
│  ⚠️ 人工干预点    │
│  策略评审会       │
└──────┬───────────┘
       │ 营销策略
       ▼
┌──────────────────┐
│  Agent: 内容生成  │
│  输入: 策略+品牌  │
│  输出: 营销内容   │
│  类型: 文案/海报  │
│  ⚠️ 人工干预点    │
│  内容审核         │
└──────┬───────────┘
       │ 营销内容
       ▼
┌──────────────────┐
│  Agent: 投放调度  │
│  输入: 内容+渠道  │
│  输出: 投放计划   │
└──────┬───────────┘
       │ 投放计划
       ▼
┌──────────────────┐
│  Agent: 效果追踪  │
│  输入: 投放数据   │
│  输出: 效果报告   │
│  异常: 效果不佳   │
└──────────────────┘
```

#### 触发条件

| 条件 | 类型 | 说明 |
|------|------|------|
| 每 30 分钟 | 定时 | 增量新闻采集 |
| 关键词命中 | 事件 | 竞品/行业关键词 |
| 营销活动前 | 事件 | 活动策划启动 |
| 手动触发 | 人工 | 临时营销分析 |

#### 步骤详情

| 步骤 | Agent | 输入 | 输出 | 涉及系统 | 人工干预 | 异常处理 |
|------|-------|------|------|----------|----------|----------|
| 1. 新闻采集 | 新闻采集 Agent | 关键词、信源 | 结构化新闻 | 新闻抓取 | 无 | 信源失效→切换备用 |
| 2. 趋势分析 | 趋势分析 Agent | 新闻+历史 | 趋势报告 | 新闻抓取 | 无 | 数据不足→降级分析 |
| 3. 竞品监控 | 竞品监控 Agent | 竞品列表 | 竞品动态 | 新闻抓取 | 无 | 竞品信息缺失→跳过 |
| 4. 策略生成 | 策略生成 Agent | 趋势+竞品+品牌 | 营销策略 | 营销系统 | **评审会** | 策略冲突→人工决策 |
| 5. 内容生成 | 内容生成 Agent | 策略+品牌规范 | 文案/海报/视频 | 多媒体宣传 | **内容审核** | 内容违规→重新生成 |
| 6. 投放调度 | 投放 Agent | 内容+渠道+预算 | 投放计划 | 营销系统 | 无 | 渠道故障→切换渠道 |
| 7. 效果追踪 | 效果追踪 Agent | 投放数据 | 效果报告 | 营销系统 | 无 | 效果不佳→自动优化 |

#### 异常处理路径

```
异常: 内容生成失败
  ├─ 路径A: 降级为模板内容
  ├─ 路径B: 人工撰写
  └─ 路径C: 跳过该内容类型

异常: 投放渠道故障
  ├─ 路径A: 切换备用渠道
  ├─ 路径B: 延迟投放
  └─ 路径C: 人工通知

异常: 效果不佳
  ├─ 路径A: 自动 A/B 测试
  ├─ 路径B: 调整投放策略
  └─ 路径C: 人工复盘
```

```

  ├─ 路径B: 人工调查
  └─ 路径C: 标记为待定

异常: 多因并存
  ├─ 路径A: 权重分析
  ├─ 路径B: 专家会诊
  └─ 路径C: 全面整改

异常: 公关风险高
  ├─ 路径A: 紧急公关
  ├─ 路径B: 法务介入
  └─ 路径C: 监管报备
```

#### 2.6.2 批次追溯链主键设计

**追溯链 = 双向链表结构**，以 `batch_id` 为主锚点、`trace_node` 为链节点：

```
正向链（原料 → 成品 → 渠道）：
  material_batch_id --(投料关系)--> batch_id --(包装关系)--> sale_batch_id
                                                       --(出库)--> order_id / logistics_no

反向链（渠道 → 成品 → 原料）：
  order_id --> sale_batch_id --> batch_id --> material_batch_id[] （1:N，多原料）
```

**关键表：trace_node（追溯节点表）**

| 字段 | 类型 | 说明 |
|------|------|------|
| trace_id | ULID | 链节点唯一 ID（ULID：时间有序 + 随机，便于按时间扫描） |
| batch_id | FK | 归属生产批次 |
| node_type | enum | INPUT(投料)/PROCESS(工序)/QC(质检)/PACKAGE(包装)/OUTBOUND(出库)/SALE(销售) |
| node_ref_type | enum | 引用对象类型：workorder/qc_record/order/... |
| node_ref_id | string | 引用对象 ID（多态关联） |
| prev_trace_id | ULID | 前驱节点（反向追溯用） |
| occurred_at | timestamp | 业务发生时间（非入库时间） |
| operator_id | FK | 操作员工（员工管理系统的 employee_id） |

> **追溯查询模式**：给定任意 `trace_id`/`batch_id`/`order_id`，沿 `prev_trace_id` 反向遍历（召回）或沿业务外键正向遍历（扩散），最坏 O(N)，N=单批次节点数（典型 <1000）。生产实现建议图数据库或宽表 + 递归 CTE。

#### 2.6.3 跨系统数据统一标识（ID 映射）

各业务系统（ERP/MES/门店/CRM/HR）主键体系互不相通，中台层建立 **全局映射表 `id_mapping`**：

| 字段 | 说明 |
|------|------|
| global_id | 中台统一 ID（ULID），中台内所有 Agent 交互只认 global_id |
| source_system | 来源系统枚举：ERP/MES/CRM/STORE/HR/SOCIAL |
| source_key | 来源系统主键值 |
| entity_type | 实体类型（对应 2.6.1 实体表） |
| version | 版本号，主数据变更时递增 |

**规则**：
1. **写入即映射**：数据接入层（Collect Agent / API Adapter）落库时同步生成 global_id 映射，业务代码不再感知来源系统主键；
2. **主数据归一**：产品/原料/门店/员工等主数据以 ERP 为权威源，其他系统的同义实体通过 `merge_rule`（名称归一化 + 编码对照表）合并到同一 global_id；
3. **不可变原则**：global_id 一经生成不变，来源主键变更仅追加新映射行，保留历史可追溯。

### 2.9 工作流联动关系

> **问题背景**：5 个工作流不能是孤岛——质量追溯发现问题要反哺生产调度，危机预警要联动营销决策。本节定义跨工作流的事件与触发规则。

#### 2.9.1 联动关系图

```
                    ┌─────────────────┐
        产能需求     │  2.1 生产调度     │←──────────────┐
      ┌────────────→│  Workflow       │               │
      │             └────────┬────────┘               │
      │                      │ 批次完成/质检异常        │ 召回→调整排产
      │                      ↓                        │
┌─────┴──────────┐   ┌─────────────────┐    ┌─────────┴────────┐
│  2.4 新品研发    │   │  2.3 质量追溯     │    │ 2.5 危机预警      │
│  Workflow      │   │  Workflow       │───→│ Workflow        │
└─────┬──────────┘   └─────────────────┘    └────────┬────────┘
      │ 上市计划            质检异常→追溯召回            │ 负面舆情分级
      │ ↓                                         ↓
      └────────────→ ┌─────────────────┐ ←───────────┘
       新品推广计划   │  2.2 营销决策     │   舆情→暂停/撤回投放
                    │  Workflow       │
                    └─────────────────┘
```

#### 2.9.2 跨工作流事件定义

| 事件名 | 发布方 | 订阅方 | 载荷关键字段 | 触发动作 |
|--------|--------|--------|--------------|----------|
| QC.ABNORMAL_DETECTED | 质量追溯 | 生产调度 | batch_id、异常项、等级 | 暂停该批次后续工序，生成复检工单 |
| QC.RECALL_DECIDED | 质量追溯 | 生产调度、营销决策、危机预警 | sale_batch_id、范围 | 召回工单、撤回相关内容、启动舆情预案 |
| SENTIMENT.LEVEL_RAISED | 危机预警 | 营销决策 | 事件等级、话题、影响产品 | 等级≥高：暂停相关投放，推送应对方案 |
| SENTIMENT.RESOLVED | 危机预警 | 营销决策 | 事件 ID | 恢复投放（需 MKT_MGR 确认） |
| RND.LAUNCH_APPROVED | 新品研发 | 生产调度、营销决策 | product_id、上市日期、目标量 | 生成新增产能评估任务、生成上市推广计划 |
| SCHED.CAPACITY_SHORTAGE | 生产调度 | 新品研发、营销决策 | 缺口量、约束 | 触发供应协商或销售节奏调整建议 |
| ORDER.SPIKE_DETECTED | 数据分析(事件总线) | 生产调度 | store/product、环比倍数 | 触发补货排产建议 |

#### 2.9.3 事件实现约定

1. **通道**：事件经中台消息总线（MCP 网关内嵌事件主题，v2 可替换为 NATS/Kafka）投递，**至少一次（at-least-once）** 语义，订阅方必须幂等（以 `event_id` 去重）；
2. **顺序**：同一 `batch_id`/`product_id` 的事件保证有序（按分区键路由）；
3. **失败处理**：订阅方处理失败进入重试队列（3 次退避），仍失败则转人工任务并告警 SYS_OPS；
4. **联动审计**：每次事件触发产生的跨工作流动作，在 8.2.4 审计模型中以 `triggered_by_event_id` 关联，保证全链路可解释。

## 5. 接口标准设计

### 5.1 MCP (Model Context Protocol)

#### 5.1.1 协议规范

MCP 用于 Agent 之间的上下文共享与能力调用。

```
┌──────────────┐         ┌──────────────┐
│  MCP Client  │◄───────►│  MCP Server  │
│  (Agent A)   │  JSON-RPC │  (Agent B)  │
└──────────────┘         └──────────────┘
```

#### 5.1.2 数据格式

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "method": "tools/call",
  "params": {
    "name": "sales_forecast",
    "arguments": {
      "store_id": "S001",
      "days": 7
    }
  }
}
```

#### 5.1.3 认证方式

```http
Authorization: Bearer <mcp_token>
X-Request-ID: <trace_id>
X-Client-ID: <agent_id>
```

#### 5.1.4 错误处理

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "error": {
    "code": -32603,
    "message": "Internal error",
    "data": {
      "original_error": "Model inference timeout",
      "retry_after": 5
    }
  }
}
```

#### 5.1.5 示例代码

```python
import httpx
from mcp_client import MCPClient

client = MCPClient(
    server_url="http://mcp-server:8080",
    token="your-mcp-token"
)

# 调用 Agent 能力
result = await client.call_tool(
    tool_name="sales_forecast",
    arguments={"store_id": "S001", "days": 7}
)

# 获取 Agent 状态
status = await client.get_agent_status("sales_forecast_agent")
```

### 5.2 A2A (Agent-to-Agent)

#### 5.2.1 协议规范

A2A 用于远程 Agent 调用，支持同步/异步两种模式。

```
┌──────────────┐         ┌──────────────┐
│  A2A Client  │◄───────►│  A2A Server  │
│  (调用方)    │  HTTP   │  (被调用方)  │
└──────────────┘         └──────────────┘
```

#### 5.2.2 数据格式

**同步调用**：
```http
POST /a2a/v1/agents/{agent_id}/invoke
Content-Type: application/json

{
  "task_id": "task-001",
  "parameters": {
    "input": "销售数据预测"
  },
  "timeout": 30000
}
```

**异步调用**：
```http
POST /a2a/v1/agents/{agent_id}/invoke-async
Content-Type: application/json

{
  "task_id": "task-001",
  "parameters": {
    "input": "销售数据预测"
  },
  "callback_url": "https://caller.com/callback"
}
```

#### 5.2.3 认证方式

```http
Authorization: Bearer <a2a_token>
X-Request-ID: <trace_id>
X-Client-ID: <agent_id>
```

#### 5.2.4 错误处理

```json
{
  "code": 429,
  "message": "Rate limit exceeded",
  "retry_after": 60
}
```

#### 5.2.5 示例代码

```python
from a2a_client import A2AClient

client = A2AClient(
    base_url="http://a2a-server:8081",
    token="your-a2a-token"
)

# 同步调用
result = await client.invoke(
    agent_id="sales_forecast_agent",
    parameters={"store_id": "S001", "days": 7},
    timeout=30000
)

# 异步调用
task_id = await client.invoke_async(
    agent_id="trend_analysis_agent",
    parameters={"keywords": ["白酒", "市场"]},
    callback_url="https://marketing-system/callback"
)
```

### 5.3 REST API

#### 5.3.1 协议规范


#### 5.3.2 数据格式

**请求**：
```http
POST /v1/workflows/production-scheduling/invoke
Content-Type: application/json

{
  "trigger": "scheduled",
  "parameters": {
    "date": "2026-04-18",

  }

```

**响应**：
```json
{
  "code": 200,

  "data": {
    "workflow_id": "wf-001",
    "status": "running",
    "trace_id": "trace-abc123"
  }
```

#### 5.3.3 认证方式

```http
Authorization: Bearer <jwt_token>
X-Request-ID: <trace_id>
X-Client-ID: <client_id>
X-Timestamp: <unix_timestamp>
X-Signature: <hmac_signature>
```

#### 5.3.4 错误处理

| HTTP 状态码 | 错误码 | 说明 |
|-------------|--------|------|
| 400 | INVALID_PARAM | 参数错误 |
| 401 | UNAUTHORIZED | 未授权 |
| 403 | FORBIDDEN | 无权限 |
| 404 | NOT_FOUND | 资源不存在 |
| 429 | RATE_LIMIT | 请求频率超限 |
| 500 | INTERNAL_ERROR | 内部错误 |
| 503 | SERVICE_UNAVAILABLE | 服务不可用 |

#### 5.3.5 示例代码

```python
import requests
from requests.auth import HTTPBearerAuth

class DSHClient:
    def __init__(self, base_url, token):
        self.base_url = base_url
        self.token = token
        self.session = requests.Session()
        self.session.auth = HTTPBearerAuth(token)

    def invoke_workflow(self, workflow_id, parameters):
        response = self.session.post(
            f"{self.base_url}/workflows/{workflow_id}/invoke",
            json={
                "trigger": "manual",
                "parameters": parameters
            },
            headers={
                "X-Request-ID": generate_trace_id(),
                "X-Client-ID": "enterprise-client"
            }
        )
        return self._handle_response(response)

    def _handle_response(self, response):
        if response.status_code == 200:
            return response.json()
        elif response.status_code == 429:
            raise RateLimitError(response.json())
        else:
            raise APIError(response.json())
```

## 8. 通用企业化解决方案

> 本章是全文的**聚合产出**：从酒厂锚点场景（§2）与行业扩展（§3–§4）中，抽取与具体行业无关的通用设计，回答"如何把单项目做成市场通用的企业级产品"。四个核心问题：Agent 如何协作、人如何介入、出错如何回滚、多企业如何共栖。

### 8.1 Agent 协作范式

#### 8.1.1 三种标准范式

中台层面统一定义三种协作范式，各工作流按步骤选用，**不允许每个工作流自行发明协作方式**：

**范式 A：管道式（Pipeline）**

```
Agent1 ──output──→ Agent2 ──output──→ Agent3 ──→ 终态
```

- 语义：上一个 Agent 的输出即为下一个的输入，串行推进；
- 适用：步骤间强依赖、每步可独立验收的场景；
- 中台实现：工作流引擎顺序编排节点，前序节点失败即中断（走 8.3 回滚）；
- 典型使用：生产调度的"数据汇总→需求预测→排程生成"段。

**范式 B：黑板式（Blackboard）**

```
            ┌── Agent1(读/写) ──┐
            │                   │
共享上下文 ──┤── Agent2(读/写) ──┤── 汇总者(收敛终态)
(Blackboard)│                   │
            └── Agent3(读/写) ──┘
```

- 语义：共享上下文（结构化黑板对象），各 Agent 并行读写不同分区，由汇总者收敛；
- 适用：多源并行分析、无严格先后依赖的场景；
- 中台实现：黑板对象 = 带 schema 的 JSON 文档（存于工作流上下文存储），各 Agent 声明 `read_keys`/`write_keys`，写冲突以 `write_keys` 互斥校验，汇总者订阅 `blackboard.completed` 事件收敛；
- 典型使用：危机预警的"多源情感分析→影响面评估→舆情分级"段；质量追溯的"多源证据采集"段。

**范式 C：主从式（Orchestrator-Worker）**

```
        ┌── Worker1 ──┐
调度者 ──┼── Worker2 ──┼── 聚合 → 终态
(路由/重试/兜底)      └── Worker3 ──┘
```

- 语义：调度 Agent 负责任务拆分、路由、重试与兜底，Worker 只做原子能力；
- 适用：步骤动态、需要条件分支/重试/多候选择优的场景；
- 中台实现：调度者 = LLM 驱动的路由 Agent（受 8.3 的状态机约束，LLM 只在合法状态间转移），Worker = 已注册的原子 MCP Tool/Agent；
- 典型使用：营销决策的"内容生成→多渠道适配→择优投放"段；新品研发的"多方案生成→评审"段。

#### 8.1.2 范式选型矩阵（通用）

| 判断维度 | 管道式 | 黑板式 | 主从式 |
|----------|:--:|:--:|:--:|
| 步骤间依赖 | 强依赖 | 弱依赖 | 动态 |
| 并行收益 | 无 | 高 | 中 |
| 步骤可预知 | 完全可预知 | 可预知 | 不可预知 |
| 失败处理成本 | 低（中断即回滚） | 中（需局部收敛） | 高（需调度者兜底） |
| LLM 成本 | 低 | 中 | 高（路由消耗） |
| 典型占比建议 | ~50% | ~30% | ~20% |

**选用规则**：能管道则管道；需要并行汇聚用黑板；只有当步骤路径依赖运行时数据（分支、重试、多候选）才用主从。

#### 8.1.3 控制流与业务逻辑流分离（复用率的关键）

行业间差异分析（§3.3、§4.3 复用矩阵）表明：工作流"骨架相似、血肉不同"。为兑现复用率承诺，将工作流显式拆分为两层：

| 层 | 内容 | 复用率 | 归属 |
|----|------|:--:|------|
| **控制流** | 编排、状态机、重试/回滚、人工干预、审计、监控 | ~100%（跨行业通用） | 核心组件·工作流引擎 |
| **业务逻辑流** | 每个节点的 Agent 实现、数据模型、阈值策略 | 行业定制 | 行业组件 |

**修订复用率口径**：原 §4.4 复用矩阵中"工作流 80% 复用"过于乐观。修正为：**控制流 100% + 业务逻辑流行业定制，工作流整体复用率 50%–60%**（其余为行业定制）。该口径同时修正 §6.3 的排期依据。

### 8.2 人工干预设计规范

> 企业系统里最复杂的是人工环节。所有工作流的人工干预点必须按本节四要素（粒度、超时、协作、留痕）声明，缺一不可。

#### 8.2.1 操作粒度（三档）

| 粒度 | 说明 | UI 能力 | 适用 |
|------|------|---------|------|
| **整体通过/驳回** | 对整个待审对象一次性决策 | 通过、驳回（附意见） | 低风险、标准流程 |
| **字段级修改** | 审批人可直接修改对象内的指定字段 | 表单编辑 + 修改留痕 | 排产计划、投放计划等"数字型"对象 |
| **局部替换/重跑** | 驳回并指定某个节点重新执行 | 选择重跑节点 + 输入约束 | LLM 生成类内容不满意 |

#### 8.2.2 超时与升级策略（按风险等级配置）

| 风险等级 | 超时时间 | 超时后动作 | 升级链 |
|----------|:--:|-----------|--------|
| 低（如常规内容确认） | 24h | **自动通过**（记录"超时自动通过"） | 无 |
| 中（如排产计划审批） | 8h | 保持挂起 + 提醒 | → 直属上级（4h） |
| 高（如召回、大额投放） | 2h | **自动驳回**（宁慢勿错） | → 部门总监（1h）→ VP（30min）→ 短信/电话触达 |

**规则**：
1. 高风险动作**禁止自动通过**，超时自动驳回并升级；
2. 升级链每级超时未响应继续上移，最终触达值班负责人（对接通知服务）；
3. 自动通过/自动驳回都必须落审计日志（8.2.4），与人工操作同权重可追溯。

#### 8.2.3 多人协作模式

| 模式 | 语义 | 配置方式 | 典型场景 |
|------|------|----------|----------|
| 串行审批 | 依次逐人审批，任一驳回即终止 | `approver: [A, B, C], mode: serial` | 工单变更（组长→经理） |
| 并行会签 | 全部通过才生效，任一驳回即不通过 | `approver: [A, B], mode: all` | 召回执行（QC_DIR + CRISIS，见 2.8.2） |
| 或签 | 任一人通过即生效 | `approver: [A, B], mode: any` | 值班响应类操作 |
| 加签 | 审批中临时追加审批人 | 审批界面上加签 | 特殊/越权场景 |

#### 8.2.4 干预留痕（审计事件模型）

每次人工干预生成一条不可变的审计事件：

```json
{
  "audit_id": "01J...",                      // ULID
  "action_type": "APPROVE | REJECT | MODIFY | RERUN | TIMEOUT_AUTO_PASS | TIMEOUT_AUTO_REJECT | ESCALATE",
  "object_type": "workorder | campaign | recall_order | ...",
  "object_id": "...",
  "object_snapshot_before": { ... },         // 修改前完整快照（字段级修改时必填）
  "object_snapshot_after":  { ... },         // 修改后完整快照
  "field_diff": ["volume_l: 5000 -> 4800"],  // 字段级修改的差异清单（自动生成）
  "approver_id": "employee-...",             // 对接 2.8 权限体系
  "roles": ["PROD_MGR"],
  "comment": "人工审批意见",
  "triggered_by_event_id": "...",            // 若由 2.9 联动事件触发，关联事件 ID
  "trace_id": "...",                          // 关联分布式链路（§7.4）
  "occurred_at": "2026-04-18T10:00:00Z"
}
```

**要求**：审计事件 append-only 存储，保留 ≥3 年（涉及召回的 ≥5 年），支持按 object_id / approver_id / trace_id 三向检索。

### 8.3 异常回滚与补偿机制

> §2 各工作流的异常处理路径均为"向前处理"。企业级系统必须补充**向后回滚/补偿**设计。采用 Saga 模式：每个工作流步骤声明其补偿动作，失败时逆序补偿。

#### 8.3.1 步骤分类与回滚点

| 步骤类型 | 示例 | 回滚语义 |
|----------|------|----------|
| **只读** | 数据查询、情感分析 | 无需补偿，直接跳过 |
| **可逆写** | 生成草稿、创建内部对象 | 逆序执行补偿：删除/置失效 |
| **已确认写** | 排程入库、订单提交 | 补偿动作 = 语义化撤销（作废而非物理删除） |
| **不可逆** | 内容对外投放、通知外部供应商 | **不可自动回滚**：执行前强制人工审批（8.2）+ 撤回预案 |

#### 8.3.2 补偿动作表（酒厂场景示例）

| 触发场景 | 已完成步骤 | 补偿动作 | 执行方式 |
|----------|-----------|----------|----------|
| 排程已下发，采购审批被驳回 | 生产工单已生成 | 工单置 `CANCELLED` + 通知 MES 取消 + 记录原因 | 自动，失败转人工 |
| 内容已投放一半发现违规 | 3/5 渠道已发布 | 已投放渠道执行**撤回 API**（平台支持则自动，否则人工工单）+ 未投放渠道冻结 + 全量留证 | 自动+人工混合 |
| 多节点工作流中间失败 | 前序 N 步已完成 | 按 8.3.1 分类逆序补偿，只读步骤跳过；补偿结果生成 `workflow_rolled_back` 审计事件 | 自动 |
| 召回执行后批次恢复合格 | 召回单已建、营销已撤回 | 反向事件 `QC.RECALL_CANCELLED` 通知订阅方恢复（营销恢复需 MKT_MGR 确认） | 事件驱动（2.9） |

#### 8.3.3 不可逆动作防护（强制规则）

1. **审批前置**：所有不可逆动作在权限矩阵（2.8.2）中必须为 ○ 或 ○/✓ 双签；
2. **双人复核**：召回、大额投放（阈值：单次费用 > 10 万元）等动作启用会签；
3. **撤回预案先行**：不可逆动作提交时必须同时提交"撤回方案"字段（如何撤、谁负责、时限），缺省不允许提交；
4. **演练**：每季度对不可逆动作做一次撤回演练（沙箱环境），验证撤回路径有效性。

#### 8.3.4 数据一致性保障

- **幂等**：所有 Agent 与补偿动作以 `workflow_instance_id + step_id + attempt_no` 作幂等键，重复投递不产生重复副作用；
- **最终一致**：跨系统副作用（如通知 MES）采用"本地消息表 + 对账任务"：中台先落本地状态，异步同步，定时对账（15 分钟）发现不一致即告警；
- **补偿失败处理**：补偿动作失败 → 进重试队列 → 3 次失败后创建最高优先级人工工单，工作流实例标记 `NEEDS_MANUAL_RECOVERY`，禁止静默丢弃。

### 8.4 多租户架构设计

> §6.3 规划 Q3 交付"多企业、同行业"的行业版。多租户是中台（而非单项目）的分水岭，架构前置如下。

#### 8.4.1 隔离策略（三档，按产品形态选择）

| 档位 | 产品形态 | 数据隔离 | 计算隔离 | 成本 | 适用 |
|------|----------|----------|----------|------|------|
| L1 物理隔离 | 专有部署版 | 独立数据库实例 | 独立主机/集群 | 高 | 金融/医疗等强合规客户 |
| L2 逻辑隔离（schema） | 行业 SaaS 版 | 同库不同 schema/库 | 共享集群，配额隔离 | 中 | 同行业多企业（主推） |
| L3 行级隔离 | 社区/试用版 | 同表 `tenant_id` 行级过滤 | 共享 | 低 | 试用、演示 |

**实现约定**：
1. 所有业务表带 `tenant_id` 列（L3）或按 schema 前缀（L2）；数据访问层强制注入租户谓词，禁止业务代码手写跨租户查询；
2. 租户上下文（`tenant_id`）经 JWT 声明传入，MCP 网关校验后写入链路上下文（§7.4 trace 扩展字段）；
3. L2 档位下，行业组件运行于共享进程池，但 **LLM 调用按租户配额与密钥隔离**（各租户用自己的模型 API Key，费用与限流互不影响）。

#### 8.4.2 行业组件共享与互不干扰

```
                 组件注册表 (Registry)
                 ┌────────────────────────┐
                 │ component              │
                 │  - id / version        │
                 │  - visibility_domain   │  ← CORE: 全租户可见
                 │  - industry_tags[]     │  ← INDUSTRY: 按 tag + 订阅关系
                 │  - tenant_bindings[]   │  ← CUSTOM: 仅绑定租户可见
                 └───────────┬────────────┘
        租户A(酒厂)           │            租户B(餐饮)
   ┌──────────────────┐      │       ┌──────────────────┐
   │ 订阅: CORE+白酒行业 │←────┼──────→│ 订阅: CORE+餐饮行业 │
   │ + 自定义2个        │      │       │                   │
   └──────────────────┘      │       └──────────────────┘
```

**规则**：
1. **三层可见域**：CORE 组件全租户共享（一份代码，多租户运行）；INDUSTRY 组件按"行业标签 + 租户订阅"共享；CUSTOM 组件仅属创建租户；
2. **版本灰度**：共享组件升级采用"新版本并行注册 → 租户逐个切换 → 旧版本下线"，避免一个租户的问题影响全部；
3. **数据不可跨租户**：行业组件内禁止缓存租户数据到共享层（如全局向量库必须带 `tenant_id` 分区，检索前置过滤）。

#### 8.4.3 租户配置、权限与配额

| 管理面 | 载体 | 要点 |
|--------|------|------|
| 租户配置 | `tenant_config`（JSON，带版本） | 启用的工作流集、组件版本绑定、模型路由策略、通知渠道、SLO 等级 |
| 权限 | 2.8 RBAC 的租户命名空间 | 角色/权限点定义全租户一致（复用），**用户-角色绑定按租户隔离**；行业角色（如 QC_DIRECTOR）仅在订阅对应行业模板时启用 |
| 配额 | `tenant_quota` | 每日 LLM Token 上限、并发工作流数、存储容量、API QPS；超限返回 429 并告警租户管理员 |

### 8.5 非功能设计

#### 8.5.1 容量与水平扩展

| 项 | 单实例容量基线（4C8G） | 扩展策略 |
|----|------------------------|----------|
| 并发工作流实例 | ~200（其中活跃 ≤50） | 实例无状态 → 水平加节点，任务经队列分发 |
| Agent 并发调用 | ~100 | Agent 运行时无状态 → 按队列深度自动扩容 |
| MCP tools/call QPS | ~500（不含 LLM） | MCP 网关无状态 → 前置 LB 水平扩展 |
| LLM 调用吞吐 | 受上游 API 限流约束 | 多 Key 池化 + 多模型路由（DeepSeek/其他）分摊 |
| 数据接入吞吐 | ~5k 条/分钟 | 按数据源分区并行，消费者组横向扩展 |
| 工作流上下文存储 | ~50 GB | 对象存储 + 生命周期策略（90 天归档） |

**削峰原则**：LLM 调用是瓶颈资源，所有进入 LLM 的任务统一排队（优先级队列：告警处置 > 人工交互 > 批处理），避免上游限流导致雪崩。

#### 8.5.2 性能指标

引用 §2.7.2 系统 SLO，补充两条全局指标：

| 指标 | 目标 | 说明 |
|------|------|------|
| 工作流启动延迟 P99 | ≤5s | 从 API/事件触发到首个节点执行 |
| 人工干预唤醒延迟 P99 | ≤10s | 审批完成后下一节点被调度 |

#### 8.5.3 可靠性设计

**单点故障清单与降级方案**：

| 单点 | 影响 | 降级方案 |
|------|------|----------|
| MCP 网关 | 全部工具调用不可用 | 多实例 + LB；网关不可用时工作流暂停排队（不丢任务），恢复后续跑 |
| 工作流引擎 | 新工作流无法启动，已运行实例状态持久化于 DB | 引擎多实例选主；实例状态落库，崩溃后由存活节点接管续跑 |
| LLM API | 所有 Agent 推理不可用 | 多供应商路由（主：DeepSeek；备：其他兼容 API）；全不可用 → 工作流转"降级模式"：仅执行确定性规则步骤，LLM 步骤挂起待恢复 |
| 消息总线 | 联动事件（2.9）不可达 | 至少一次投递 + 持久化队列；总线故障时事件落本地消息表，恢复后补投 |
| 数据库 | 全局不可用 | 每日全备 + WAL 增量，RPO ≤ 5min、RTO ≤ 30min；恢复演练每季度一次 |

**数据一致性**：见 8.3.4（幂等键 + 本地消息表 + 对账）。

#### 8.5.4 成本估算模型（单工作流运行成本）

```
单次工作流成本 ≈ Σ(各节点 LLM Token 费用) + 基础设施摊销/调用次数

示例（营销决策·单次内容生产，按 DeepSeek 定价量级估算）：
  情感分析节点     ~50k tokens ≈ ¥0.5
  内容生成节点     ~120k tokens ≈ ¥1.2
  多渠道适配(×5)   ~250k tokens ≈ ¥2.5
  合计 LLM        ≈ ¥4.2/次
  基础设施摊销    ≈ ¥1.0/次（按 4C8G×3 实例月成本 ¥3000 ÷ 月均 3000 次调用）
  合计            ≈ ¥5.2/次
```

**成本治理**：`tenant_quota` 按上表口径设定预算；每次工作流实例记录实际 Token 消耗，月度出租户成本报表，超预算 80% 预警。

### 8.6 MVP 选型与实施节奏

#### 8.6.1 MVP 工作流选型修订

MVP 原则应为"**最快验证核心架构、最少外部依赖**"。按依赖强度重排：

| 工作流 | 外部依赖 | 数据准备量 | MVP 结论 |
|--------|----------|-----------|----------|
| **危机预警** | 仅舆情数据源（爬虫即可启动） | 小 | **✅ 纳入 MVP（P0）** |
| 营销决策 | 依赖危机预警产出 + 投放渠道 API | 中 | **✅ 纳入 MVP（P0）**（与危机预警形成最小闭环，验证 2.9 联动） |
| 生产调度 | ERP/MES/门店三系统集成 | 大 | 延后至 P1（集成成本最高） |
| 质量追溯 | 完整批次数据链 | 大 | 延后至 P1（数据准备最重） |
| 新品研发 | 依赖以上产出 | — | P2 |

**修订后 MVP = 危机预警 + 营销决策**：两个工作流即覆盖"事件总线 → 黑板式协作 → 人工干预 → 审计 → 联动事件"全部核心架构件，且外部集成最轻。

#### 8.6.2 实施节奏修订（原计划 → 修订）

| 里程碑 | 原计划 | 修订 | 修订理由 |
|--------|--------|------|----------|
| MVP 上线（2 工作流） | 8 周上线 5 工作流 | **12 周**：MVP 2 工作流（含多租户 L2 骨架、审计、回滚框架） | 人工干预/回滚/审计需要实打实的开发量 |
| P1（生产调度+质量追溯） | 与 MVP 同批 | MVP 后 +16 周 | 三系统集成 + 批次数据治理前置 |
| 全 5 工作流 | 8 周 | **~28 周（约 7 个月）** | 含用户培训与运维体系建设 |
| 第二行业（餐饮） | 首年后 3 个月 | 首年后 **6 个月** | 行业版 = 行业组件 + 数据模型 + 场景验证，3 个月不现实 |
| 4 行业覆盖 | 12 个月 | **24 个月** | 医疗合规认证本身 ≥6 个月 |
| 开放生态/技能市场 | 2026 Q4 | **2027 H2** | 生态前提是组件体系稳定 + 多租户成熟 |

> 节奏修订约为原计划的 1.5–2 倍，与 §8.1.3 的复用率修正（50–60%）一致。各阶段准出条件：MVP 准出 = 危机预警+营销决策在生产环境稳定运行 4 周、SLO 达标（§2.7.2）、至少 1 次真实召回/撤回演练通过。

| 风险 | 影响 | 概率 | 应对措施 | 责任角色 |
|------|:--:|:--:|----------|----------|
